==============================================================
Agent Team Design
プロジェクト: AWS Serverless Data Platform (mHealth ETL)
バージョン: 1.0.0
最終更新: 2026-02-23
==============================================================

1. Agent Teamsの導入目的
-------------------------
mHealthデータ基盤において、以下の複合的な探索タスクを
並列化・分業化することで品質と速度を向上させる:

- データ理解の多角的探索（品質/EDA/ガバナンス/特徴量の同時進行）
- 単一Agentでは見落としがちな観点の網羅的なカバー
- 各Agentが独立コンテキストで動作することによる思考の汚染防止

前提: 実行系は禁止。設計・生成・検証のみ。
      破壊系操作は .claude/settings.json の hooks で自動ブロック。


2. Agent構成と責務
------------------

[Agent 0] Orchestrator（Leader）
  役割:
    - ユーザーの目的を整理し、仮説に分解する
    - 各Agentへのタスク割当を行う
    - 各Agentの成果物を統合し、最終アウトプットを生成する
    - 矛盾する結論を調停する（最終判断はOrchestratorのみが行う）
  独立性:
    - 他のAgentの中間結果には直接アクセスしない
    - 各Agentの完了報告を受けてから統合を開始する
  禁止事項:
    - 実行系操作の委任（他のAgentに対しても実行を命じない）
    - 未確認の仮説を確定的な結論として扱う

[Agent 1] Data Intake Agent
  役割:
    - データの所在を整理する（S3パス/ファイル形式/サイズ目安）
    - 抽出設計を行う（実取得はしない、設計のみ）
    - データパイプラインのリスクを指摘する
  使用スキル: data-intake
  入力: Orchestratorからのデータソース情報
  出力: データ所在マップ + 抽出設計書 + リスク一覧
  独立性:
    - Quality Agent・EDA Agentとコンテキストを共有しない
    - 自身の判断でデータにアクセスしない

[Agent 2] Quality Agent
  役割:
    - スキーマ契約を整理する（カラム/型/NULL/値域）
    - 欠損・異常値の観点を提示する
    - 将来のデータ品質テストの観点を列挙する
  使用スキル: schema-contract
  入力: Orchestratorからのスキーマ情報
  出力: スキーマ契約書 + 品質チェックリスト + 整合性検証観点
  独立性:
    - Data Intake Agentとコンテキストを共有しない
    - 実際のデータに触れずにスキーマを定義する

[Agent 3] EDA Agent
  役割:
    - 分析仮説を生成する
    - EDA観点を拡張する（見落とされがちな角度を提示）
    - ノートブックテンプレートを設計する
  使用スキル: eda-notebook, sql-generator
  入力: Orchestratorからの分析目的
  出力: 分析仮説リスト + EDAノートブックテンプレート + 検証SQL草案
  独立性:
    - Feature Agentとコンテキストを共有しない
    - 小サンプル前提で設計し、大規模実行は提案しない

[Agent 4] Feature Agent
  役割:
    - 特徴量の候補を生成する
    - データリーク観点を整理する
    - 特徴量エンジニアリングの設計書を作成する
  使用スキル: sql-generator, schema-contract
  入力: Orchestratorからの予測目的
  出力: 特徴量候補リスト + リーク観点チェックリスト + 特徴量設計書
  独立性:
    - EDA Agentと独立して動作する（視点の汚染を防ぐ）
    - 学習・推論コードの実行は行わない

[Agent 5] Governance Agent
  役割:
    - PIIリスクを評価する
    - 承認レベルを明示する
    - コンプライアンス上の懸念を報告する
  使用スキル: data-governance-guard
  入力: Orchestratorからのデータカラム情報
  出力: PIIリスク分類表 + 承認マトリックス + コンプライアンスチェックリスト
  独立性:
    - 他のAgentの判断に引きずられず、独立してリスク評価する
    - 「このデータは安全だ」という他Agentの前提を盲信しない


3. 通信フロー
-------------
以下のフローで動作する（並列実行フェーズあり）:

Phase 1: 初期化（Orchestrator）
  - ユーザー目的の受け取り
  - 仮説・タスクへの分解
  - Agent割当の決定

Phase 2: 並列探索（Agent 1〜5が独立して同時稼働）
  - Data Intake Agent  → データ所在マップ + リスク一覧
  - Quality Agent      → スキーマ契約書 + 品質チェックリスト
  - EDA Agent          → 分析仮説 + ノートブックテンプレート
  - Feature Agent      → 特徴量候補 + リーク観点
  - Governance Agent   → PIIリスク評価 + 承認マトリックス

Phase 3: 統合（Orchestrator）
  - 各Agentの成果物を収集する
  - 矛盾・競合を解消する（例: EDA Agentが提案したカラムにGovernanceがリスクを検出）
  - 最終レポートを生成する
  - 次のアクションを人間に提示する

Phase 4: 人間のレビュー
  - 最終レポートをレビューする
  - 実行が必要な操作（SQL実行、Glue Job起動等）を人間が行う
  - フィードバックをOrchestratorに返す（次サイクルへ）


4. トークン消費前提
-------------------
Agent Teamsはトークンコストが高い。以下の原則で最小化する:

- 各Agentのコンテキストウィンドウは独立させ、全履歴を共有しない
- Orchestratorへの報告は要約形式（詳細は別ファイルに保存）
- 並列探索は「本当に多角的な視点が必要なタスク」に限定する
- 単純なタスク（SQL1本の生成等）はAgentを使わずSkillを直接呼ぶ


5. 誤った結論の収束防止設計
-----------------------------
単一Agentや反復対話では、誤った前提が固定化するリスクがある。
以下の設計でこれを防ぐ:

(1) 独立コンテキスト
    - 各Agentは他Agentの中間結果を見ない
    - これによりAgent間の思考汚染を防ぐ

(2) Governance Agentの独立性の強化
    - Governance Agentは他のAgentが「安全」と判断した場合でも
      独自にリスク評価する。他Agentの楽観的判断に引きずられない。

(3) Orchestratorの調停ルール
    - 複数AgentがAとBで矛盾する場合、OrchestratorはA/Bどちらかを
      一方的に採用せず、両方をユーザーに提示して判断を仰ぐ
    - Governance Agentが「高リスク」を報告した場合は、
      他Agentの成果物があっても実行には進まない

(4) 最終確認の人間介在
    - 「実行してよいか？」の判断は常に人間が行う
    - Claudeは「設計・提案」はするが「決定・実行」はしない


6. 並列探索の使い所
-------------------
Agent Teamsを使うべきタスク:
  - 新しいデータソースの全体評価（品質/EDA/ガバナンスを一気に評価）
  - 特徴量エンジニアリングの多角的探索
  - コンプライアンス観点を含む設計レビュー

Agent Teamsを使わずSkillを直接使うべきタスク:
  - 特定のSQL1本の生成（sql-generatorを直接呼ぶ）
  - スキーマ定義の確認（schema-contractを直接呼ぶ）
  - 簡単なPIIチェック（data-governance-guardを直接呼ぶ）


7. 将来の拡張計画
-----------------
P1: MCP連携Agent
  - S3読み取り専用MCPを通じて実際のメタデータを取得するAgentを追加
  - Glue Catalogとの自動同期機能をAgent経由で提供

P2: 自動品質チェックAgent
  - CI/CD連携Agent: PRマージ時に自動でスキーマ変更を検出・報告
  - コスト監視Agent: Athenaクエリコストの定期レポートを生成
