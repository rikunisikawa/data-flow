1. 3階層実行モデル
==============================================================

すべての操作を「生成」「読み取り実行」「副作用あり実行」の3レベルに分類する。

--------------------------------------------------------------
L1: 生成のみ（自動OK）
--------------------------------------------------------------
定義:
  ファイルの生成・編集のみ。データへのアクセスなし。副作用なし。

対象操作:
  - SKILL.md / テンプレートファイルの生成
  - SQLの生成（実行しない）
  - ドキュメントの作成・更新
  - data_contract.yamlの作成
  - Git add / commit（push は禁止）

承認不要: Claudeが自律実行してよい。

フック制御: なし（デフォルト許可）

--------------------------------------------------------------
L2: 読み取り実行（条件付き・上限あり）
--------------------------------------------------------------
定義:
  データへの読み取りアクセス。書き込みなし。コスト上限あり。

対象操作:
  - S3からのサンプルダウンロード（許可パスのみ、先頭100行まで）
  - Athenaでのクエリ実行（SELECT文のみ、スキャン上限$10以内）
  - Glue Catalogの読み取り（スキーマ確認のみ）

承認プロセス:
  1. エンジニアがL2操作であることを確認する
  2. コスト見積もりを確認する（Athenaなら推定スキャンサイズ）
  3. データオーナーにSlack等で口頭確認する
  4. 実行後にログを記録する

上限制御:
  - Athenaクエリ: $10/回 上限（Workgroupで強制）
  - S3読み取り: 許可リストパスのみ（/raw/ への直接アクセスは禁止）
  - サンプルサイズ: 1000行以内

フック制御: settings.jsonのhooksでblock → 手動でオーバーライドして実行

--------------------------------------------------------------
L3: 副作用あり（承認必須）
--------------------------------------------------------------
定義:
  書き込み・削除・デプロイ・外部送信など、元に戻しにくい操作。

対象操作:
  - S3への書き込み
  - ETL/Glue Jobの実行
  - dbt run の実行
  - Lambdaのデプロイ
  - Terraformのapply
  - レポートの外部配布（メール・Slack）
  - データベースへのDML

承認プロセス:
  1. PRを作成する（成果物は [要L3承認] ラベルを付ける）
  2. テックリード + データオーナーがレビューする
  3. 両者が LGTM した場合に人間が実行する
  4. 実行ログを記録する（CloudTrail / アプリケーションログ）
  5. 問題が発生した場合はrunbook_incident.txtに従う

フック制御: settings.jsonのhooksで常時block

2. プロンプトインジェクション対策
==============================================================

データと命令の混同リスクへの設計原則:

--------------------------------------------------------------
最小権限
--------------------------------------------------------------
- Claudeに与えるデータアクセス権限は必要最小限にする
- S3の読み取り対象は /stage/, /processed/ のみ（/raw/ は禁止）
- Claudeのコンテキストにsecrets（APIキー・接続文字列）を含めない

--------------------------------------------------------------
分離
--------------------------------------------------------------
- 「データの内容」と「Claudeへの命令」を明確に分離する
- データファイルを直接Claudeのプロンプトに貼り付けない
  → 代わりにデータのメタデータ（スキーマ・件数）のみを渡す
- Agent TeamはAgent間でコンテキストを共有しない（独立コンテキスト）

--------------------------------------------------------------
監査
--------------------------------------------------------------
- すべてのAI生成物はGitにコミットする（変更履歴を保持する）
- Claudeが生成したSQL・設計書は人間がレビューしてから実行する
- 本番操作はCloudTrail / S3アクセスログで記録する

--------------------------------------------------------------
上限制御（サンプル/コスト）
--------------------------------------------------------------
- Athenaクエリには常にLIMIT句を付ける（本番実行時はWORKGROUPで上限強制）
- サンプルサイズは最大1000行
- 大規模処理の前にコスト見積もりを確認する

3. PII（個人情報）ガバナンス
==============================================================

--------------------------------------------------------------
PII分類
--------------------------------------------------------------
本プロジェクトのPII疑いデータ:
  - ECGデータ（ecg_lead1, ecg_lead2）: 生体情報 → 中リスク
  - タイムスタンプ（秒単位以下）: 特定可能性あり → 低リスク
  - その他センサ値: 匿名 → リスクなし

分類基準:
  高リスク: 単独で個人特定が可能なデータ（氏名・メールアドレス等）
  中リスク: 組み合わせで個人特定可能なデータ（生体情報・位置情報等）
  低リスク: 単独では特定不可だが注意が必要なデータ

--------------------------------------------------------------
PII取り扱いルール
--------------------------------------------------------------
- PIIカラムを含む分析はL2承認（データオーナー確認）が必要
- PIIカラムを外部共有する場合はL3承認（法務確認）が必要
- PIIを含む成果物には機密ラベル（confidential / restricted）を付ける
- PIIを含むデータをClaudeのコンテキストに直接渡さない
- マスキング済みデータのみをL1/L2レベルで扱う

--------------------------------------------------------------
同意と規制
--------------------------------------------------------------
- Kaggle mHealthデータセットの利用規約を遵守する
- 被験者データの二次利用は利用規約の範囲内に限る
- 生体情報（ECG）の医療診断目的への使用は禁止

==============================================================
4. secrets管理ルール
==============================================================

禁止事項:
  - コードファイルへのAPIキー・接続文字列の直書き
  - Gitリポジトリへのsecretsのコミット（.gitignoreで制御）
  - Claudeのコンテキスト（プロンプト）へのsecretsの貼り付け
  - ログファイルへのsecretsの出力

許可される管理方法:
  - AWS Secrets Manager（本番推奨）
  - 環境変数（.env.dev ファイル、Gitignore済み）
  - GitHub Actions Secrets（CI/CD用）

定期ローテーション:
  - APIキーは90日以内にローテーションする
  - ローテーション手順はrunbook_incident.txtに記載する
